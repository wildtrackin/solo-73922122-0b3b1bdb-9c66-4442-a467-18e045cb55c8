# 报警日志网关 · 双采集进程入仓与取证打包演示

模拟工厂网关把 JSONL 报警日志（设备号 / UTC 时间 / 报警码）写入共享目录，
两个独立采集进程持续把日志入仓到同一个 SQLite 检索库，并通过网页控制网关、
观察采集结果、按设备和 UTC 闭区间**离线取证打包**。重点演示**改名轮转、旧文件
补写、并发采集、进程中断重启**下**不漏行、不重复**，以及取证期间采集不中断、
证据只来自受理瞬间的同一入仓快照。

## 一、组件

| 组件 | 文件 | 职责 |
|---|---|---|
| 网页服务 | `app/main.py` | FastAPI：网关控制 + 入仓结果查询 + 取证接单/查询/下载 + 单页控制台 |
| 网关模拟器 | `app/gateway.py` | 追加 JSONL、写半行、**仅改名轮转**（不删除/不截断，最多 3 件）、旧文件补写 |
| 采集器 | `app/collector.py` | 扫描共享目录，按文件身份与字节位点精确入仓（每个容器跑一个进程，共两个） |
| 取证打包 | `app/forensics.py` | 受理即冻结同一入仓快照，后台流式打 ZIP、逐条/逐字节校验、SHA-256、重启清扫 |
| 存储层 | `app/db.py` | SQLite（WAL），表结构、事务与并发连接 |
| 配置 | `app/config.py` | 全部参数走环境变量 |

## 二、怎么保证不漏、不重

1. **文件身份与改名无关。** 用 `(st_dev, st_ino)` 生成 `file_id`。网关把
   `alarms.jsonl` 改名为 `alarms.1.jsonl` 并新建同名空文件后，旧 inode 仍按新
   路径被跟踪；之后对旧文件的补写（backfill）照样入仓，新文件是另一个身份。
2. **位点与数据同一事务提交。** 每个文件的已提交字节位点 `read_offset` 与
   新插入的报警行在同一个 `BEGIN IMMEDIATE` 事务里提交。读取或写库失败时事务
   回滚，位点不前进，下一轮从旧位点重读——因此**不会跳过未入仓部分**。
3. **唯一约束兜底防重。** `alarms` 上有
   `UNIQUE(file_id, byte_offset)`，插入用 `INSERT OR IGNORE`；两个采集器竞争时
   同一物理行最多入仓一次。同文不同行（字节偏移不同）各自保留；内容完全相同
   的两条记录也作为不同行保留。
4. **只入完整行。** 只消费到最后一个换行符；末尾没有换行的记录留在磁盘上，等
   补全后再入仓。各文件独立推进，一个文件的半行**不会阻塞**其它文件（含新建
   的活动文件）。
5. **跨块读取。** 单条记录大于 `READ_CHUNK` 时，一次扫描内累积读取直到遇到换行
   或 EOF，避免长行把位点永久卡死；超过 `MAX_LINE_BYTES` 仍无换行则挂起并报错，
   绝不静默截断。
6. **WAL + busy_timeout + 启动重试。** 多进程共库使用 WAL；连接时对
   `journal_mode=WAL`（该 pragma 不受 busy_timeout 保护）做带退避的重试，避免
   两个采集器同时启动时因瞬时写锁直接退出。

## 三、轮转规则

* 只做 `rename`：`alarms.jsonl → alarms.1.jsonl`，世代号顺延（`.1→.2`…），随后
  立刻创建同名空文件；**不删除、不截断任何文件**。
* 目录内最多 `MAX_GENERATIONS=3` 个 `.jsonl`；达到上限再轮转会被拒绝（HTTP 409），
  从源头保证旧文件不丢失。
* 旧文件依旧可以追加（网页下拉选择旧文件名即可补写）。

## 四、取证打包（证据保全）

调查员把一段报警连同源件交给同事离线核对，取证期间采集仍在继续。打开
**取证页 `/forensics`**，按 `device_id`（精确匹配）和 UTC **闭区间**（上下界都
包含，必须是带 `Z` 或 `+00:00` 的 ISO-8601 UTC 时间）受理一单，后台生成 ZIP。

### 4.1 证据为什么不会被后续数据污染

1. **受理即冻结同一入仓快照。** 取证单、明细 `forensics_items`、源件快照
   `forensics_file_snapshots` 在**同一个 `BEGIN IMMEDIATE` 事务**写入。明细的
   文件身份（inode 派生的 `file_id`）、字节偏移，以及各源件**截至该快照已提交
   的字节位点** `prefix_bytes` 一并冻结。
2. **只复制已提交前缀。** 打包按身份重新解析路径（改名也能找到同一 inode），
   从 0 起**仅流式复制 `prefix_bytes` 字节**；受理后的追加、以及没有换行的
   未完成行都落在前缀之外，天然排除。
3. **改名/轮转/补写不串件、不失败。** 条目按 `file_id` 归档，源件以
   `(st_dev, st_ino)` 匹配而非信任路径；轮转后旧 inode 改了名也能定位，新建的
   同名文件是另一个身份，不会混进同一证据条目。
4. **逐条 + 逐字节校验，不过即整单失败。** 先做 ZIP CRC 检查，再把每个源件的
   整个前缀与实时源件（同一身份）分块比对并算 SHA-256，同时顺序遍历包内字节，
   把**每条明细原文与包内对应字节逐一比对**。任何不符或读写异常都删除临时包、
   把单据置 `failed` 并记录原因，**失败/进行中的单子不开放下载**。
5. **全程流式，内存恒定。** 受理明细、校验、manifest 都用游标分批（500 行/批），
   文件按 `FORENSICS_CHUNK`（默认 1 MiB）分块；启用 ZIP64，源件大于 4 GiB 也能
   打包。实测 160 MiB 源件在 128 MiB 地址空间限制下打包成功，峰值 RSS 约 31 MiB。

### 4.2 ZIP 内容

```
manifest.json                 明细：每条记录的 file_id / 行号 / 字节偏移 / 长度 /
                              原始行 / 设备 / UTC / 报警码 / 源路径 / 对应 ZIP 条目
SHA256SUMS.txt                manifest 与各源件前缀的 SHA-256
README.txt                    取证单与闭区间说明
sources/<file_id>/<文件名>     该源件受理时已提交位点之前的原始字节前缀
```
ZIP 自身也计算 SHA-256 与字节大小并落库，页面可查。

### 4.3 状态与重启语义

* 单据状态：`pending → running → succeeded / failed`，页面可查状态、失败原因、
  源件快照与明细，并下载成功包（`GET /api/forensics/jobs/{uid}/download` 流式
  返回，不整包进内存）。
* **中断重启**：服务启动时把遗留的 `pending/running` 单一律置 `failed`（原因注明
  重启中断）并清理临时包；失败后可重新受理取证。**已成功的包不受影响，继续可
  下载。**
* 采集与打包互不阻塞：打包在 web 进程的单后台线程运行，两个采集器仍持续入仓，
  网关追加、旧件补写、连续轮转照常完成。

## 五、运行

```bash
docker compose up --build
# 打开 http://localhost:8000
```

启动三个容器：`web`（FastAPI，限内存 128 MiB）、`collector-a`、`collector-b`，
共享三个卷：`shared_data`（JSONL 目录）、`db_data`（SQLite）、
`evidence_data`（取证 ZIP，临时包与成品都落盘，不占内存）。

网页功能：
* 控制台 `/`：追加完整记录 / 写无换行半行 / 补换行 / 改名轮转；展示采集进程
  心跳、目录文件与 inode、每个文件的已提交字节位点、入仓记录（含 file_id、行号、
  字节偏移、源路径、采集者）、采集错误。
* 取证页 `/forensics`：受理取证单、查看状态与失败原因、浏览源件快照与明细、
  下载 ZIP。

## 八、已知边界

* 轮转世代号靠文件名约定；若有人在共享目录手工改名，身份仍以 inode 为准，只是
  世代排序可能变化。
* SQLite 适合本演示规模与单机共享卷场景；更高吞吐可平移到 Postgres 等，采集器
  的“位点与数据同事务”模型不变。
* 不处理文件被外部截断（合同约定网关只追加/改名）；若检测到文件变短会记录错误
  并冻结该文件位点，避免静默错位。取证复制时若发现源件身份消失或前缀字节与
  快照不一致，整单失败而非部分交付。
* 取证按单台 web 进程内的单个后台线程串行打包（顺序清晰、便于审计）；需要更高
  取证吞吐时可把 worker 拆成独立容器，快照与校验模型不变。
